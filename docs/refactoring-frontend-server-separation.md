# Frontend/Server Code Separation Refactoring

## Summary

This refactoring cleanly separates frontend and server code in the authentication and Convex adapter modules. The changes enable better mocking and testing by isolating server-only logic from client-accessible code.

## Changes Made

### New Directory Structure

```
src/
├── auth/
│   └── types.ts                 # Shared type definitions
├── server/
│   ├── auth-utils.ts            # Server-only JWT token creation
│   └── convexAdapter.ts         # Server-only NextAuth adapter for Convex
├── auth.ts                      # NextAuth configuration (imports from server modules)
└── components/
    └── AppProviders.tsx         # Updated to use shared types
```

### Files Created

1. **`src/auth/types.ts`** - Shared type definitions
   - Exports common types (Session, AdapterUser, etc.) that can be safely imported by both client and server code
   - Prevents direct imports from next-auth in client components

2. **`src/server/auth-utils.ts`** - Server-only authentication utilities
   - Contains `createConvexToken()` function for JWT generation
   - Marked with `'server-only'` directive
   - Manages private key caching
   - Previously embedded in `src/auth.ts`

3. **`src/server/convexAdapter.ts`** - Server-only Convex adapter
   - NextAuth adapter implementation for Convex database
   - Marked with `'server-only'` directive
   - Handles all database operations for user, session, account management
   - Moved from `src/lib/convexAdapter.ts`

### Files Modified

1. **`src/auth.ts`**
   - Removed inline JWT token creation logic
   - Now imports `createConvexToken` from `@/server/auth-utils`
   - Now imports `ConvexAdapter` from `@/server/convexAdapter`
   - Cleaner, more focused on NextAuth configuration

2. **`src/components/AppProviders.tsx`**
   - Changed Session type import from `next-auth` to `@/auth/types`
   - Maintains client-side functionality without mixing concerns

### Files Deleted

1. **`src/lib/convexAdapter.ts`** - Replaced by `src/server/convexAdapter.ts`

## Benefits

1. **Clear Separation of Concerns**
   - Server-only code is marked with `'server-only'` directive
   - Client components use shared types instead of importing server modules
   - Build-time errors if server code is accidentally imported on client

2. **Better Testability**
   - Server logic can be mocked independently
   - JWT token creation logic is isolated and testable
   - Convex adapter can be replaced with test doubles

3. **Maintainability**
   - Related functionality is grouped in dedicated directories
   - Smaller, more focused files
   - Clear import paths indicate code boundaries

4. **Type Safety**
   - Shared types prevent type mismatches
   - TypeScript enforces correct usage across boundaries

## Implementation Notes

### Server-Only Directive

The `'server-only'` package is used at the top of server modules:

```typescript
import 'server-only';
```

This ensures these modules cannot be imported by client components. Next.js will throw a build error if attempted.

### ESLint Configuration

Added inline comments to suppress import resolution errors for Convex-generated files:

```typescript
// eslint-disable-next-line import/no-unresolved -- Convex generates these files at build time
import { api } from '@/convex/_generated/api';
```

These files are generated by the Convex CLI during development/build and won't exist in the repository.

### Migration Path

If other parts of the codebase need similar refactoring:

1. Identify mixed server/client code
2. Extract server-only logic to `src/server/`
3. Create shared types in `src/auth/types.ts` or similar
4. Update imports to use new paths
5. Add `'server-only'` directive to server modules
6. Test that server code cannot be imported on client

## Testing Impact

This refactoring was done specifically to improve testability. Future work should:

1. Mock `@/server/auth-utils` in auth tests
2. Mock `@/server/convexAdapter` in NextAuth configuration tests
3. Test client components without needing server dependencies
4. Use shared types for consistent test fixtures
